## 1. Problem 与 Goal

### 1.1 问题（一句话）

`dailyMinutes` 从未进入派词计算——用户在目标三问答的「每天几分钟」只被存下来回显，从不影响派多少词；同时题型仍由用户手选、默认停在再认，复习不随 `lvl` 升级为回忆。**N4 不是「加档位」，是「补链路」**（v3.0 §0.3/附录 A-10）：档位按钮已经存在，缺的是从「档位」到「今日派词量」的那一段计算。

因果链（【推断】，依据 §2【实测】）：`goal.dailyMinutes` 三问写入 → `buildPlan` 只读 `g.type`/`g.deadline` 不读它 → `estMinutes` 是「按词数反算」的输出 → `computeDailyBudget` 只看 `planDailyFresh`/`freshLimit`/`reviewRatio`/`reviewLimit` → 用户答的时长对派词零影响。接线之后，6 条既有缺陷会**真的改变用户任务量或让设置值不可信**，故必须同批修（§5）。

### 1.2 目标

1. **N4**：让 `settings.dailyMinutes` 成为唯一真源并真正驱动今日派词量；计划页 / 设置页展示值与派词执行值同源；三问「当初答的时长」可回显。
2. **N2**：复习额度内的卡按 `lvl` 自动上移题型（再认 → 带提示产出 → 关提示全拼），让回忆成为默认路径；只改「怎么再见」，不改「何时再见」。
3. **同批修复** 6 条既有缺陷，使接线后的显示值可信、档位合法、封顶同源、估算不失真、14 天图不把空打开日画成 0% 柱。
4. **不触碰红线**：`SCHEMA` 保持 3、`LADDER_DAYS` 固定阶梯为可回退基线、评级三分支零改动。

> 本文**不承诺任何活跃度 / 留存提升**（沿用 v3.0 §2.5 定性）：修完的可验收效果是「设置页数字不再自己往下掉 + 时长真的决定派词量 + 复习默认走回忆」。以「活跃度」作判据属定性错误。

## 5. 关键合并判据（DoD 硬门禁）

> 以下 5 条为**合并判据**，任一不满足即判定本批「未完成」，不得以「分批交付 / 先上一半」结案。

### 5.1 展示值与执行值同源

`settings.dailyMinutes` 是**唯一真源**。派词执行值、计划卡 / 设置页回显值、`estMinutes` 估算必须与之同源；任一读取路径读 `goal.dailyMinutes`、读写死值、或两处封顶各自实现，即视为未完成。判据覆盖「设置页 10 / 计划页 20」与「派 12 词 / 卡显示 20」两类同源病（N4W-AC02/03/08/11）。

### 5.2 两处封顶须同时改

`computeDailyBudget`（`js/core.js:641`）与 `planCardDailyFresh`（`js/core.js:899`）的 `freshLimit` 封顶必须**同批改**；只改前者会出现「今日派 12 词、计划卡显示 20」，是 §5.1 同源病换了位置复发（N4W-AC08）。

### 5.3 只交付其一视为未完成（两层）

- **层一（N4 × N2）**：`N4W` 段 12 条与 `N2L` 段 11 条必须同时交付；只交付任一段 = 未完成。
- **层二（N4 内部同批）**：「① `dailyMinutes` 接线 ② 两处封顶同源 ③ D-1~D-6 六条缺陷修复」必须同批；分批 = 未完成（v3.0 §2.1「三件必须同批发布，禁止分批」；只改下限不改接线 = 「改了但没效果」的假修复）。

### 5.4 SCHEMA 保持 3，新字段走 `ensureSchema` 幂等加法

`db.schema` 恒为 **3**；`db.ladder` 等新字段只在 `ensureSchema` 以「缺失才补」方式追加，重复调用无变化不写盘、不加「只跑一次」版本标记；导出 / 导入整库克隆天然兼容（N4W-AC10、N2L-AC01/11）。抬到 4 会让旧版本拒绝导入新备份，属红线。

### 5.5 回归门禁

全量 7 文件 **161 项 0 失败** + `check-data.mjs` **460 词通过**；新测试写独立文件、精确更新 3 条断言期望值、其余 158 项逐字不动、项数仍 161（K6）；`LADDER_DAYS` 与 `rateWord` 三分支零改动（N4W-AC12、N2L-AC10）。
