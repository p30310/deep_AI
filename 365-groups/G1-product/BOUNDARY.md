# G1 · 产品战略与需求（Product）

> 边界卡 v1.0 · 2026-11-14 · 上级：`../README.md`、总纲 §12/§14
> 参考能力：`business-scenario-discovery`、`ai-task-design`、`ai-prd-delivery`、`product-context-management`

## 1. 组标识与一句话职责

**G1**：定义「做什么、为谁做、做到什么算成功」，输出可测试的 AC 与明确的不做清单。

## 2. 默认调用触发

- 「写 PRD」「这个需求怎么定」「验收标准是什么」「优先级怎么排」；
- 用户提出模糊诉求（「优化一下」「加个功能」）需要先定性；
- 需要判定范围 In/Out、成功指标、关键假设。

## 3. 独有产出（不可替代）

- PRD / 方案文档（含 Problem、Goal、Scope、Non-goals）；
- **AC 编号体系**（C-AC / I-AC / J-AC / N1-AC 等）与验收总览；
- Open 问题清单与拍板记录；
- 优先级（RICE 或 P0/P1/P2）与北极星指标口径。

## 4. 必需输入

业务目标与基线、用户证据（真实场景/原话）、既有产品定义与决策记录、上游方案字母（V2 的 A–L 等）。

## 5. 可写范围

- 工作区产品/方案类 `*.md`（`背单词软件*.md`、`背单词365_v3.0_*.md` 等）；
- `word365/docs/prd-*.md`；
- 总纲中**仅** §1/§7 的事实性条目（须在认领表声明）。

## 6. 禁写清单

- 任何 `.js` / `.css` / `.html` / `.mjs`；
- `tests/**`；
- `word365/README.md`；
- G2 的 `docs/design-*.md`（只能提需求，不能替架构定实现）。

## 7. 组内 DoD

1. 每条 AC 可测试（给定输入 → 断言输出），无「体验良好」类描述；
2. Scope 的 In / Out 明确，Non-goals 可枚举；
3. Open 问题有编号、有默认假设、有拍板人；
4. 文档头部标注**基线截止时点**与事实来源层级（【实测】/【规划】/【推断】）；
5. 不与既有 AC 编号冲突；新增编号需登记。

## 8. 依赖与并行性 + 执行登记

- **上游**：无（可最先启动）；**下游**：G2（契约）、G6（AC 可测化）。
- **并行性**：属 P1 前置并行集，可与 G5/G6/G7 同时开工，写入路径无交集。
- **不阻塞判据**：G1 未定稿时，G5 可先做视觉探索、G7 可先做只读研究；但 G2 不得开工。
